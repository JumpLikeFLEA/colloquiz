### Implied CHARS_PER_TOKEN by depth

Raw JSONL chars ÷ real context tokens, at four points through each session.

| session | @25% | @50% | @75% | @deepest |
|---|---:|---:|---:|---:|
| `bb01cb0a` | 5.57 | 6.00 | 6.22 | **6.53** |
| `5910d6c5` | 6.21 | 7.13 | 7.51 | **7.77** |
| `86fb8134` | 9.04 | 9.32 | 9.27 | **9.57** |
| `34f091ff` | 5.61 | 6.20 | 6.60 | **6.82** |

The value rises with depth in all four. Mechanism: the system prompt, tool
definitions and MCP schemas sit in the token count while contributing zero
chars, so they depress the ratio early and amortise away as the transcript
grows. Every `@deepest` figure is therefore a floor on that session's
content-only ratio, not its asymptote.

### Peak occupancy vs. what the guard reported

`chars / 4 / 1_000_000` against the transcript's own `message.usage` sum at
the same point. **Occupancy here is `input_tokens + cache_creation_input_tokens
+ cache_read_input_tokens` — output_tokens excluded.** This differs from the
`occupiedTokens()` function shipped in `context-guard.mjs`, which adds
`output_tokens`; see "Occupancy definition" in the parent ADR for why the two
are not reconciled here.

## Derived figures

Arithmetic over the four values above, not printed by the probe.

- Range: **6.53 – 9.57**. Spread max/min = **1.47×**.
- Median: (6.82 + 7.77) / 2 = **7.295**.
- With a best-fit constant of 7.295, the hard limit (0.45) fires at a real
  occupancy of `0.45 × 7.295 / R`:
  - R = 9.57 → **34.3%**
  - R = 6.53 → **50.3%**

  A 16-point window of uncertainty around a 5-point soft/hard band, within
  one project's density profile.
- Real peak occupancy across the four: 50.2% / 40.5% / 31.4% / 42.0% — the
  0.40 / 0.45 fractions sit where real sessions actually end.

## Not established by this run

- **What causes the between-session spread.** The obvious candidate fails:
  `toolUseResult` duplication is *lowest* (6.2%) in the transcript with the
  *highest* ratio (9.57) and highest (13.0%) in a middling one. No
  explanation is recorded because none was measured.
- **Sidechain behaviour.** 0.0% in all four, so the sample contains no
  subagent entries and says nothing about whether `isSidechain` is the field
  they carry, or whether they carry `message.usage` at all. (Resolved by a
  later, separate measurement — see "Sidechain layout" in the parent ADR.)
- **`CONTEXT_WINDOW_TOKENS`.** Nothing here compacted and the maximum
  occupancy observed is 501,962, so the 1M window is neither confirmed nor
  refuted by this data. (Also resolved separately — see "Compaction-boundary
  validation" in the parent ADR.)
