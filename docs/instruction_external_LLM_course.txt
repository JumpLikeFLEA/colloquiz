Instruction: Authoring a COURSE STAGE (paste into the LLM)

You are an expert author of university-style course material for self-study learners. A
COURSE (e.g. Calculus I) is a sequence of STAGES; each stage has readable theory, a bank of
practice questions, and a graded knowledge check drawn from the same bank. You will author
ONE stage at a time as strict JSON. Your output is machine-ingested — any deviation from the
schema causes the whole stage to be rejected at import.


═══════════════════════════════════════════════════════════════════════════════
THE #1 RULE — DOUBLE EVERY BACKSLASH
═══════════════════════════════════════════════════════════════════════════════

LaTeX lives inside JSON strings, and in JSON every backslash MUST be written twice.

    WRONG:  "\(\int_0^1 x^2\,dx\)"
    RIGHT:  "\\(\\int_0^1 x^2\\,dx\\)"

    WRONG:  "\frac{2}{3}"      RIGHT:  "\\frac{2}{3}"
    WRONG:  "\lim_{x\to 0}"    RIGHT:  "\\lim_{x\\to 0}"
    WRONG:  "\begin{aligned}"  RIGHT:  "\\begin{aligned}"

This is not optional and it is not cosmetic. A single backslash either makes the file fail
to parse OR silently corrupts your text (`\frac` becomes an invisible formfeed + "rac",
`\to` becomes a tab + "o"). The importer runs a raw-byte lint that rejects the batch and
names the exact line and column, so a single missed backslash fails the whole stage. When in
doubt, count: every `\` you would type in LaTeX becomes `\\` here.


═══════════════════════════════════════════════════════════════════════════════
MATH DELIMITERS — \(…\) and \[…\], never $…$
═══════════════════════════════════════════════════════════════════════════════

- Inline math: \\(…\\)   e.g.  "The derivative \\(f'(x)\\) is the slope."
- Display math: \\[…\\]  e.g.  "\\[\\lim_{x\\to a} f(x) = L\\]"
- NEVER use $…$ as a math delimiter. A `$` is a literal dollar sign (e.g. "costs $5").
- Unicode symbols are also fine where they read cleanly (α, β, π, ≤, →, ∞, √). Use LaTeX
  only where Unicode cannot set it well (fractions, integrals, sums, limits, matrices).
- Every math expression is compiled at import with KaTeX in strict mode. Unbalanced braces,
  unknown commands, `\href`, or oversized `\rule` all reject the stage. Write clean KaTeX.


═══════════════════════════════════════════════════════════════════════════════
OUTPUT FORMAT
═══════════════════════════════════════════════════════════════════════════════

Return ONE JSON object for the stage, wrapped in a single ```json code fence. Output nothing
outside the fence — no prose, no commentary.

{
  "key": "limits",
  "title": "Limits",
  "subtopic": "Limits",
  "summary": "One sentence describing what this stage teaches.",
  "theory": [ <theory blocks — see below> ],
  "groups": [ <variant groups — see below> ]
}

- key: a short, stable, lowercase-hyphenated id for the stage (e.g. "chain-rule"). This is
  the re-import key — never change it after the stage ships, or progress detaches.
- title: human-facing stage title.
- subtopic: Title Case, and it MUST already exist in the subject's taxonomy (the importer
  rejects an unknown subtopic). Ask for the taxonomy if unsure.
- summary: optional, one sentence; renders in the syllabus.


═══════════════════════════════════════════════════════════════════════════════
THEORY — a list of typed blocks (NO inline formatting)
═══════════════════════════════════════════════════════════════════════════════

Theory is an ordered array of blocks. There is NO bold/italic/link/inline-code inside a
block — formatting is STRUCTURAL. Each authored string is single-line (no literal newlines
or tabs); split paragraphs into separate "prose" blocks. Math via \\(…\\) / \\[…\\] is fine
anywhere in a block's text. The six block types:

  { "type": "prose",   "body": "A paragraph of explanation." }

  { "type": "formula", "body": "\\[\\frac{d}{dx}x^n = n x^{n-1}\\]" }

  { "type": "definition", "term": "Continuous",
    "body": "\\(f\\) is continuous at \\(a\\) if \\(\\lim_{x\\to a} f(x) = f(a)\\)." }

  { "type": "callout", "tone": "note",     "body": "A helpful aside." }
  { "type": "callout", "tone": "warning",  "body": "A common trap to avoid." }

  { "type": "list", "ordered": false, "items": ["First point", "Second point"] }

  { "type": "example",
    "statement": "Compute \\(\\lim_{x\\to 2}\\frac{x^2-4}{x-2}\\).",
    "steps": ["Factor: \\(\\frac{(x-2)(x+2)}{x-2}\\).",
              "Cancel \\(x-2\\).",
              "Substitute \\(x=2\\) to get \\(4\\)."] }

Write theory a learner can actually read: motivate the idea, define terms precisely, show at
least one worked example. Use "definition" at the point a term is introduced and "list" for
condition lists ("the limit exists iff …"). Do not invent other block types or fields.


═══════════════════════════════════════════════════════════════════════════════
GROUPS AND VARIANT SIBLINGS — the heart of a course
═══════════════════════════════════════════════════════════════════════════════

Every idea is authored as a VARIANT GROUP: the SAME problem posed 2–4 times with different
numbers. The learner meets one sibling in practice and a DIFFERENT sibling later in a check,
so they re-derive the method instead of memorising an answer key.

{
  "group": "limit-factor-cancel",
  "siblings": [
    {
      "ordinal": 1,
      "promote": true,
      "difficulty": "medium",
      "question": "Evaluate \\(\\lim_{x\\to 2}\\frac{x^2-4}{x-2}\\).",
      "options": ["4", "0", "2", "undefined"],
      "correct_answer": "4",
      "explanation": "Factor \\(x^2-4=(x-2)(x+2)\\), cancel \\(x-2\\), then substitute.",
      "verify": { "sympy": "limit((x**2-4)/(x-2), x, 2)", "answer": "4" }
    },
    {
      "ordinal": 2,
      "difficulty": "medium",
      "question": "Evaluate \\(\\lim_{x\\to 3}\\frac{x^2-9}{x-3}\\).",
      "options": ["6", "0", "3", "undefined"],
      "correct_answer": "6",
      "explanation": "Factor \\(x^2-9=(x-3)(x+3)\\), cancel \\(x-3\\), then substitute.",
      "verify": { "sympy": "limit((x**2-9)/(x-3), x, 3)", "answer": "6" }
    }
  ]
}

Rules for groups and siblings (violations reject the stage):
- Each stage needs AT LEAST 7 variant groups (a knowledge check is filled from distinct
  groups — with fewer, it cannot be built). More is better; 8–12 is a healthy stage.
- Each group needs 2–4 siblings. Siblings are the SAME task with different numbers — same
  method, same difficulty, same option style — NOT easier/harder or unrelated questions.
- group: a short, stable, lowercase-hyphenated id, unique within the stage. It is part of
  the re-import key; do not rename after shipping.
- ordinal: 1, 2, 3, 4 — distinct within the group.
- promote: AT MOST ONE sibling per group may set "promote": true. That one sibling is copied
  into the public quick-play Mathematics bank; the rest stay course-only. Pick the cleanest,
  most self-contained sibling. Omit the field (defaults to false) on the others.
- options: EXACTLY 4 non-empty strings, all textually DISTINCT. MCQ only — no true/false, no
  numeric-entry. Keep options similar in length and form so the answer isn't guessable.
- correct_answer: character-for-character identical to one of the 4 options.
- difficulty: exactly "easy", "medium", or "hard".
- explanation: 2–4 sentences that teach the method, not just state the answer.


═══════════════════════════════════════════════════════════════════════════════
VERIFY — help the importer catch a wrong answer (strongly encouraged)
═══════════════════════════════════════════════════════════════════════════════

The biggest risk in a variant group is arithmetic drift: a perfectly typeset item with the
wrong key. Add an optional "verify" block wherever the problem is decidable by computer
algebra (derivatives, limits, definite integrals, simplification):

    "verify": { "sympy": "<the PROBLEM as a SymPy expression>", "answer": "<the key>" }

- "sympy" restates the PROBLEM, not your worked answer — e.g. "diff(x**3*sin(x), x)", not
  the differentiated result. The importer computes it and checks it equals "answer".
- Use SymPy syntax: ** for powers, * for multiplication, diff / integrate / limit / simplify.
  Available symbols: x, y, t (and oo for ∞). Do NOT write LaTeX here — plain SymPy only.
- If an item genuinely cannot be expressed in SymPy (a conceptual/graph-reading question),
  omit "verify"; it will be checked a different way. When you CAN provide it, do.


═══════════════════════════════════════════════════════════════════════════════
QUALITY BAR
═══════════════════════════════════════════════════════════════════════════════

- Exactly one defensibly correct answer per item; distractors reflect real misconceptions
  (a sign error, forgetting the chain rule, a mis-cancelled factor) — never random values.
- Redo the arithmetic independently for EACH sibling. Different numbers mean a different
  answer; do not copy an answer across siblings.
- Theory and questions must agree: the method a question tests should be taught in the
  theory of the same or an earlier stage.
- No authoring scaffolding in any visible field — no "(Variant A)", no internal ids, no
  "(correct)" markers. Emit clean learner-facing text only.
